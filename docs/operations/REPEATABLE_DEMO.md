# Démonstration complète pour le jury — laboratoire GitHub

**Ne jamais assimiler un exercice GitHub à une application EpiVerse développée.**

1. **Gouvernance** : montrer les décisions, la distinction Estelle direction / frontend Soumia, les incertitudes et la RACI provisoire.
2. **Issue** : sélectionner un ticket LAB, expliquer Requirement ID, WBS, priorité, risques, estimation et critères d'acceptation.
3. **Projects** : montrer tableau Kanban, sprint, calendrier, risk register, ETС et ownership après création du Project privé.
4. **PR** : examiner le lien Issue→PR, le diff, CODEOWNERS, les reviewers et les commentaires.
5. **CI** : montrer les logs réels GitHub Actions, y compris les échecs initiaux, leur diagnostic et les nouveaux runs réussis.
6. **Sécurité** : vérifier permissions minimales, dépendances, contrôles de secrets, état actuel du dépôt, accès privés.
7. **Releases** : montrer archive et draft, ne pas les appeler versions de l'application.
8. **Reporting** : démontrer compteurs issus de l'API GitHub du LAB, distinguer réalisation, test, validation et livraison.
9. **Observabilité pédagogique** : Delta Log, état des risques, décisions ADR et rétrospective.
10. **Transfert officiel** : présenter une PR de portage **future et non fusionnée**, après accord explicite.

Vérifications négatives utiles : tentative d'accès non autorisé au Project privé, PR sans Issue refusée par le contrôle, dépôt public bloquant les scripts de déploiement, données fictives identifiées.
